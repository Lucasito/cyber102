# Архитектура

Одно приложение Next.js: сайт, REST API, виджет, админка и фоновые циклы ботов. База — PostgreSQL.

Защищённые адреса (`Venue.locationLocked`), явные варианты названий (`VenueAlias`), связь зала со зданием
(`Venue.buildingId`) и очередь изменений (`DataChange`) описаны в [DATA_QUALITY.md](DATA_QUALITY.md).

```
                ┌──────────── Next.js (контейнер afisha-app) ─────────────┐
 Браузер ──────►│ app/(site)   сайт          app/admin   админка          │
 Сайт с        ►│ app/widget   виджет        app/api/v1  REST API         │
 виджетом       │ app/api/ai/chat  умный поиск                            │
                │                                                          │
 MAX ◄─────────►│ lib/server/max.ts      ┐                                │
 Telegram ◄────►│ lib/server/telegram.ts ┴► bot-core.ts ─┐                 │
 (через Worker) │                                         ▼                │
                │ lib/server/agent.ts ──► events.ts (поиск) ──► PostgreSQL │
                │        │                                                 │
                │        └──► ai.ts (очередь, повторы) ──► GigaChat / OpenAI-совм.
                │ lib/server/settings.ts ◄── таблица Setting (админка)     │
                └──────────────────────────────────────────────────────────┘
```

## Главный принцип: выдуманных событий нет

- У каждого события есть источник (`EventSource.url`), он показан на странице события.
- ИИ-агент **не создаёт** события: фильтры поиска собирает код, события берутся из БД, модель только
  объясняет готовую подборку. Список событий в ответе формирует код, а не модель.
- Тестовые события помечены источником `demo` и бывают только в локальной базе (`npm run seed:demo`, `BOOTSTRAP_DEMO=1` в
  `docker compose`) — для разработки и контрольного прогона. На продакшне — только реальные события из источников.

## Модель данных (`prisma/schema.prisma`)

| Модель | Назначение |
|---|---|
| `Event` | Событие (поля — ниже, по схеме ТЗ 8.1) |
| `EventSource` | Откуда взято событие: код и тип источника (`MANUAL`, `IMPORT`, `RSS`, `API`, `PAGE`), ссылка, хеш исходной записи. Одно событие из нескольких источников — несколько записей |
| `RawRecord` | Сырая запись источника (строка файла, элемент RSS) отдельно от события: можно переиграть нормализацию без повторного сбора. Уникальна пара источник + хеш |
| `ImportRun` | Загрузка файла: итоги и отчёт по строкам |
| `AuditLog` | Журнал изменений: кто, когда, действие, сущность, кратко и `diff` «было → стало» |
| `Venue` | Площадка: название, город, адрес, координаты (уникальна пара название + город) — справочник площадок и городов |
| `Category` | Справочник жанров: `slug` (theatre, concert, exhibition, museum, kids, cinema, festival, lecture, excursion) и название |
| `Reminder` | Напоминание из бота |
| `QueryLog` | Запросы к помощнику и трасса каждого ответа: режим, задержка, токены, стоимость, события-основания, шаги; `userKey` (IP или аккаунт бота) — для лимита стоимости |
| `BotUser` | Пользователь бота: платформа, идентификатор, последние реплики диалога (имя не хранится) |
| `AdminUser`, `AdminSession`, `AdminToken` | Пользователи админки, сессии, одноразовые ссылки из писем |
| `Setting` | Настройки из админки: раздел → JSON |

**Схема события — соответствие ТЗ 8.1:**

| ТЗ | В базе |
|---|---|
| `id` UUID | `id` (cuid — уникальная строка) |
| `title`, `normalized_title` | `title`, `normalizedTitle` |
| `category` enum | `categoryId` → `Category.slug`; «другое» — `null` |
| `tags`, `language`, `description` | `tags[]`, `language`, `description` |
| `date_start`, `date_end`, `duration_min` | `startsAt`, `endsAt`, `durationMin` |
| `city`, `venue`, `address`, `lat`, `lon` | через `venueId` → `Venue.city`, `name`, `address`, `lat`, `lon` |
| `price_min`, `price_max`, `is_free` | `priceMin`, `priceMax` (₽; `null` — неизвестно); `is_free` = `priceMin = 0` |
| `age_limit` | `ageLimit` |
| `org_link` | `orgUrl` (организатор) и `ticketUrl` (билеты) |
| `source_url`, `source_type`, `source_hash` | `EventSource.url`, `sourceType`, `sourceHash` |
| `verified_at`, `confidence` | `verifiedAt`, `confidence` |
| `status` (опубликовано, черновик, отменено) | `publication` (`PUBLISHED`/`DRAFT`) + `status` (`SCHEDULED`, `RESCHEDULED`, `CANCELLED`, `SOLD_OUT`, `PAST`) |
| `dedup_key` | `dedupKey` |
| `created_at`, `updated_at` | `createdAt`, `updatedAt` |

Дополнительно: `needsReview` и `reviewNote` (спорная карточка, очередь модерации), `originalStartsAt` (прежняя
дата при переносе), `pushkinCard`, `accessibility`, `imageUrl`.

**Видимость:** посетителям — только `publication = PUBLISHED`; в выдаче — без `CANCELLED` и `PAST`. Отменённое
открывается по прямой ссылке с пометкой; черновик по ссылке — 404.

## API, логи и метрики (`lib/server/api.ts`, `log.ts`, `metrics.ts`)

- Маршруты API обёрнуты в `apiRoute(имя, обработчик)`: идентификатор запроса `X-Request-Id` (входящий или новый),
  структурный лог одной JSON-строкой (`ts, level, event, rid, route, status, ms` — без текстов пользователей и
  контактов), метрики, ошибка `500 { code: "internal", details: { requestId } }` вместо падения.
- `cachedJson` — ETag по содержимому, `Cache-Control`, ответ 304 по `If-None-Match`.
- Метрики — в памяти процесса: запросы, 4xx, 5xx, задержки (последние 1000 на маршрут, p50/p95); `GET /api/metrics`.
- Обращения (`lib/server/feedback.ts`): одна проверка для сайта и API — схема zod, ловушка для ботов, время
  заполнения формы ≥ 3 с, не больше 5 в час с адреса, не больше 3 ссылок; письмо модераторам.

## Геокодирование (`lib/server/geocode.ts`)

Nominatim (OpenStreetMap): без ключа, доступен с сервера. Очередь — не чаще 1 запроса в 1,1 с, понятный
User-Agent, кеш в таблице `GeoCache` (в том числе «не найдено»). Применение:

- **регион события:** населённого пункта нет в `RB_SETTLEMENTS` и в списке из админки — `settlementInBashkortostan`;
  вне РБ — строка импорта отклоняется, геокодер недоступен — карточка в модерацию;
- **координаты площадок:** фоновая задача раз в 5 минут, по 5 площадок без координат — по адресу, по названию,
  в сёлах — центр населённого пункта; `Venue.geocodedAt` — чтобы не повторять ненайденное.

## Импорт и нормализация (`lib/server/import.ts`, `lib/server/normalize.ts`)

1. **Разбор файла:** CSV (разделитель `;`, `,` или табуляция, кавычки по RFC 4180) или JSON (массив,
   `{ events }`, `{ items }`). Колонки сопоставляются по названиям из ТЗ, английским и русским синонимам.
2. **Идемпотентность:** хеш канонического JSON строки; запись уже есть в `RawRecord` и стала событием — «без
   изменений». Сырые строки (в том числе отклонённые, с причиной) хранятся в `RawRecord`.
3. **Проверка:** обязательны название, дата начала, город, площадка, ссылка на источник (`http(s)`); событие не в
   прошлом; окончание не раньше начала. Не прошла — «отклонено» с причиной.
4. **Нормализация:** даты (`2026-11-14 19:00`, `14.11.2026 19:00`, «14 ноября 2026 в 19:00»; без пояса — местное
   время), цена из текста («вход свободный», «от 300 до 800 ₽»), категория по словам («музыкальный вечер» →
   concert), город к справочнику с исправлением падежей и опечаток (расстояние Левенштейна), площадка к справочнику
   по нормализованному названию.
5. **Дедупликация:** своё событие источника — по `externalId` (переживает перенос даты: статус `RESCHEDULED`,
   прежняя дата в `originalStartsAt`), иначе по `dedupKey` = нормализованное название | местная дата | площадка.
   Нашлось — обновление (в журнал — `diff`), источник добавляется к карточке.
6. **Спорные:** нет категории или цены — черновик с `needsReview` и причиной, в очередь модерации.
7. **Отчёт:** по строкам (`ImportRun.report`) и итоги: добавлено, обновлено, без изменений, отклонено.

## Сбор из внешних источников (`lib/server/collect/`)

Источники — таблица `Source` (раздел админки «Источники»). Сборщик даёт строки в формате импорта, дальше — общий
`importRows`: нормализация, регион РБ, дедупликация, проверка, что ссылка отвечает (`urlAlive`).

| Тип (`kind`) | Модуль | Как читается |
|---|---|---|
| `universal_json` | `index.ts` | JSON по [формату](../lib/format-spec.ts): массив или `{ events }` |
| `universal_rss` | `rss.ts` | RSS 2.0, поля `afisha:*` (пространство имён `urn:afisha-rb:1`), `link` — ссылка, `guid` — код |
| `jsonld` | `jsonld.ts` | `<script type="application/ld+json">` с `@type …Event` |
| `html_ai` | `fetch.ts` + `ai-extract.ts` | Страница афиши → JSON-LD, если есть; иначе текст со ссылками «текст (адрес)» кусками по 4000 символов → ИИ извлекает список событий (`extractEventList`); неизменившийся кусок (`SourceItem` с `guid = chunk:<sha1>`) повторно не разбирается |
| `rss_ai` | `rss.ts` + `ai-extract.ts` | Лента → карточка по ссылке → сначала JSON-LD карточки, нет — ИИ извлекает поля (`askJson`), несколько сеансов — несколько строк |
| `custom` | `adapters.ts` | Реестр индивидуальных парсеров `ADAPTERS`; парсеры кинотеатров — `cinemas.ts` (сеанс = событие с `externalId`, 5 дней, без ИИ; проверка `npm run test:cinemas -- --live`) |

Доверие: `rss_ai` и источник без `autoPublish` идут в импорт с `review` — новые события только черновиком в
очередь модерации, существующие не меняются (иначе обход модерации). У `rss_ai` каждая запись ленты разбирается
один раз (`SourceItem`, уникально по `sourceId + guid`), за запуск — не больше `maxItems` новых: это предел
расходов на ИИ. Расход токенов считается через `withAiUsage` и пишется в итог запуска. Пробный запуск
(`previewSource`) ничего не пишет: `validateRows` прогоняет строки через ту же нормализацию; у `rss_ai` — до 3
записей. Расписание — `collectDueSources` из `jobs.ts` раз в 10 минут, в фоне, до двух источников за раз
(`isDue`): с `collectAt` («06:00») — раз в день, когда наступило это время по Уфе и сегодня после него ещё не
собирали; без него — раз в `intervalHours` после прошлого сбора.

Площадка источника (`collect/venue.ts`): у театра или музея все события в одном здании — `Source.venueName`,
`venueAddress`, `venueLat/Lon`. `prepareRows` до импорта привязывает к нему записи без площадки или с похожим
названием (зал после запятой сохраняется) и подставляет адрес и координаты; у остальных записей город, названный в
площадке («ГДК Стерлитамак»), главнее города источника по умолчанию (`cityInVenue`). `applySourceVenue` при
сохранении источника и после сбора даёт площадкам этого здания точные координаты (из источника или по адресу).
Загрузка (`fetch.ts`): таймаут 20 с, до 3 МБ, кодировка из заголовка или объявления (UTF-8, windows-1251).
Сборщик может соблюдать `robots.txt` — переключатель в «Источниках» (`Setting.collect.respectRobots`, по
умолчанию выключено) (`robots.ts`, кеш на 6 часов): правила для `AfishaRB` или для всех (`*`), Allow /
Disallow, шаблоны `*` и `$`, побеждает самое длинное совпадение; закрытая страница — ошибка «сайт закрыл эту
страницу для роботов». `robots.txt` нет (4xx) или он не загрузился — сбор не блокируется. Проверка ленты на
`/docs/format` (её запускает владелец сайта) `robots.txt` не учитывает.

Публичная страница формата — `/docs/format` (поля и образцы — `lib/format-spec.ts`, тот же список полей, что у
импорта); проверка ленты — `POST /api/v1/format/check` (`collect/detect.ts` определяет формат по содержимому).

## Дубли между источниками (`lib/server/dedup.ts`)

Точный ключ (`dedupKey`: название + время + город + площадка) не ловит одно событие из разных источников:
«Спектакль «Любовь и голуби»» и «Любовь и голуби / Мөхәббәт һәм күгәрсендәр», «Башкирский драмтеатр» и «Башкирский
драматический театр им. Ильшата Юмагулова». Поэтому в импорте после точного поиска — нечёткий (`findDuplicate`):

- кандидаты — тот же город, начало в пределах 30 минут (у выставок — пересечение дат);
- ядро названия (`titleCore`): до « / » (перевод), без жанровых и служебных слов («спектакль», «концерт», «для
  детей»…), чисел и коротких слов, слова по основе из 6 букв; похожесть — доля общих слов от короткого названия;
- площадка — общие значимые слова по основе из 4 букв (без «театр», «государственный», «башкирский»…);
- **явный дубль** (`same`) — похожесть ≥ 0,8 и та же площадка: запись прикрепляется к существующей карточке;
  **возможный** (`possible`) — на той же площадке похожесть ≥ 0,5, на разных — ≥ 0,8 (две «Новогодние ёлки» в
  разных театрах в 11:00 — решает модератор): новое событие уходит в модерацию с `possibleDuplicateId` (`dupLevel`).
  Местоимения и служебные слова («моя», «наш», «это») в ядро не входят: «Моя тёща» и «Неспетая песня моя» — разные.

«Своё» событие (связь `EventSource` с тем же источником) источник обновляет; чужое — только дополняет пустые поля
(`FILL_FIELDS`) и добавляет ссылку на себя, иначе два источника переписывали бы карточку друг за другом. Недоверенные
данные (ИИ, организатор) существующую карточку не трогают. Модерация: у события с пометкой — карточка-оригинал и
«Объединить» (`mergeEvents`: ссылки, пустые поля и напоминания переходят к оставшейся, дубль удаляется) / «Разные
события» (`distinctFrom`); внизу — `scanDuplicates`: похожие пары по всей актуальной афише.

## Роли и кабинет организатора

`AdminRole`: `ADMIN` (2) > `MODERATOR` (1) > `ORGANIZER` (0); `requireAdmin(role)` пускает роль не ниже указанной,
поэтому все разделы с `requireAdmin("MODERATOR")` организатору закрыты автоматически (404). Каркас админки пускает
с `ORGANIZER`, каждая страница проверяет роль сама. Организатор: `/admin/my` (свои события по `Event.createdById`),
`/admin/my/new`, `/admin/my/import` — действия `app/admin/organizer-actions.ts` идут через `importRows` с `review`
(«от организатора …») и `createdById`. Модератор приглашает и отключает организаторов (`/admin/organizers`,
действия в `app/admin/actions.ts` работают только с ролью `ORGANIZER`). Самостоятельная заявка — `/organizers/apply`
(`app/(site)/organizers/apply/actions.ts`, защита как у обратной связи): учётная запись `ORGANIZER` с
`active: false, pendingApproval: true`; `signIn` при верном пароле отвечает «заявка на рассмотрении»; модератор
одобряет (`approveOrganizer`) или отклоняет — с удалением записи (`rejectOrganizer`).

В трассах (`QueryLog.userKey`) идентификатор пользователя — только хеш `ip:…` / `telegram:…` (sha256 с солью, 16
знаков): лимиты стоимости работают, а IP и id мессенджера не хранятся.

## Поиск (`lib/server/events.ts`)

Одна функция `searchEvents` для сайта, API, виджета, ботов и агента.

- Время республики — UTC+5 (`Asia/Yekaterinburg`). Дата `YYYY-MM-DD` в фильтре — начало/конец этого дня
  по местному времени.
- Период ищется по **пересечению**: событие попадает, если началось до конца периода и не закончилось до его
  начала. Поэтому идущие выставки видны в «Выходных».
- Без даты показываются ещё не закончившиеся события. Прошедшие (`PAST`) и отменённые (`CANCELLED`) скрыты, если статус
  не задан явно; черновики (`DRAFT`) не видны никогда.
- `age` — возраст зрителя: события с `ageLimit <= age` или без ограничения.
- `priceMax` сравнивается с минимальной ценой (`priceMin`); `free` — только `priceMin = 0`.
- `datePresets()` — «сегодня», «завтра», «выходные» (ближайшие сб–вс).

## ИИ-агент (`lib/server/agent.ts`, инструменты — `lib/server/agent-tools.ts`)

**Инструменты (ТЗ 7.2)** — `search_events`, `get_event`, `find_similar`, `get_venue_schedule`, `subscribe`,
`save_feedback`. Каждый возвращает JSON (`{ ok, data }` или `{ ok: false, error }`), ответ из результата собирает
агент; ошибка инструмента не подменяется догадкой. Инструмент и аргументы модель выбирает в том же вызове, что
и разбор фильтра (поля `tool`, `args`), — без лишнего запроса и задержки. Правила по тексту главнее модели:
«подпишите / присылайте новые» → `subscribe`, «передайте организатору / ошибка в карточке» → `save_feedback`,
«расписание …», «что идёт в …» → `get_venue_schedule`, «похожее на «…»» → `find_similar`, «отменили ли «…»» →
`get_event`; уточнение к прошлой подборке — всегда `search_events`. Не больше 5 вызовов на ответ (поиск и его
ослабления). Каждый вызов — шаг трассы `tool` с аргументами, результатом и тем, кто выбрал (правила / модель).
Изменение данных — только после подтверждения: `subscribe` и `save_feedback` сначала возвращают
`needsConfirmation`, агент спрашивает с кнопками «Подтвердить» / «Отмена», шаг помечается `pending`; ответ
«да» / «подтвердить» исполняет отложенное действие из трассы диалога. Подписка оформляется пользователю бота;
на сайте и в API аккаунта нет — агент даёт ссылки на ботов. Карточка события (`get_event`) и ответы на подписку
и обращение собирает код, без модели.

```
диалог ─► модель: разбор в фильтр (JSON) ─┐
       └► правила (ruleFilter)            ┴─► слияние (правила главнее)
                                               │
          ничего конкретного? ─► уточняющий вопрос (один раз) + кнопки
                                               │
          searchEvents ─► пусто? ослабить: даты → жанр → город (бюджет и возраст — никогда;
                          жанр, угаданный моделью, а не названный, — первым)
                                               │
          модель: объяснение подборки (только по списку) ─► ответ + события + кнопки-подсказки
```

- **Разбор запроса.** Модель получает весь диалог (последние 10 реплик) и собирает фильтр с учётом уточнений
  («а в воскресенье?»). Ответ модели принимается в любом виде: `{"filter": {...}}` или фильтр без обёртки.
- **Правила** (`ruleFilter`) детерминированно ловят частые условия и **перекрывают** модель — она иногда их
  теряет: «бесплатно», «сегодня/завтра/послезавтра/на выходных/на неделе», дни недели («в субботу»),
  «до 1000 ₽ / 2 тыс», «с ребёнком» (6 лет), «с подростком» (12), «с сыном 10 лет», жанры в коротких репликах
  («театр», «концерт»… — для кнопок-подсказок).
- **Уточнение** — по правилу, не на усмотрение модели: если нет ни даты, ни жанра, ни бюджета, ни возраста, ни
  города, ни названия — один вопрос «когда, с кем, что ближе» с кнопками. Повторно подряд не спрашивает.
  На реплику не про события («привет») — приветствие и тот же вопрос.
- **Пустой результат** — фильтр ослабляется по шагам, ответ начинается с «Точно под запрос ничего нет —
  показываю ближайшие варианты в другие даты…».
- **Объяснение.** Модель получает сегодняшнюю дату, применённые условия словами и список событий с днём недели
  и сроком (для выставок — «идёт с … по …»), события сегодня/завтра помечены. Стиль — короткий совет на «вы»
  («Сегодня в 17:00 — лекция …»), без служебных фраз вроде «подборка подходит». Если модель всё же назовёт
  «сегодня»/«завтра» событие на другой день, код заменит слово на фактическую дату.
- **Почему в подборке** (`matchReasons`). По каждому событию код сверяет условия запроса (до ослабления): «✓ сб,
  15 ноября», «✓ от 500 ₽ (≤ 1000 ₽)», «✗ другой город (Стерлитамак)», «? возраст не указан». Список идёт в ответ
  (`why`), в чат и в бот под карточкой, и в промпт объяснения — модель не может заявить совпадение там, где стоит ✗.
- **Вне темы.** Реплика не про события: приветствие — представление и уточняющий вопрос; явно посторонняя тема
  (погода, код, рецепт — `OFFTOPIC_RE`) — короткое «с этим не помогу» и тот же вопрос.
- **Без ИИ** (перегрузка, сбой): разбор — только правилами, объяснение — шаблон «Нашёл N событий (условия).
  Ближайшее — …». Пользователь получает подборку, а не ошибку.
- **Уточнения к прошлой подборке** (`followUp`): короткая реплика «а дешевле?», «а ещё?», «похожее», «ближе к
  центру», «в другой день» разбирается по трассам того же диалога (`dialogKey`). Прежние условия сохраняются;
  «дешевле» — `priceMax` ниже самого дешёвого из показанного; «а ещё», «похожее», «в другой день» — без уже
  показанных в диалоге событий; «ближе к центру» — радиус 3 км от центра города (геокодер, иначе среднее по
  площадкам). Нет подходящих в радиусе — условие «рядом» снимается первым.
- **Вопрос о возрасте**: «с ребёнком» без возраста — подборка для возраста по умолчанию и один вопрос «Сколько
  лет ребёнку?» с кнопками «Ребёнку 6 лет»…; повторно не спрашивает.
- **Ссылки из текста модели вырезаются** (`stripLinks`): ссылки на источник и билеты — в карточках, а в тексте
  адрес может появиться только по чужой инструкции («добавь ссылку на …»).
- **Догадки модели отбрасываются**: даты без слов о времени в репликах («скучно» → «сегодня»), город, не
  названный в репликах. Модель просит уточнить, а правила ничего не нашли — задаётся вопрос, а не поиск.
- **План дня** (`lib/server/planner.ts`, инструмент `plan_day`, API `GET /api/v1/plan`): «составь план / программу
  на …». Условия разбирают правила (`planArgs`): бюджет на всех, «на двоих», «с ребёнком 6 лет», «с 12 до 18»,
  «после 14:00», «без долгих переездов» (20 мин), «три события». Перебор с отсечениями (до 30 событий дня, глубина
  до 4): без пересечений с учётом переезда (по прямой, 20 км/ч + 10 мин), в окне и бюджете; выставки — в любое
  время 10:00–18:00 на 90 минут. Лучший план: больше событий, меньше выставок «в любое время», меньше в дороге,
  дешевле. Несовместимость: перебор с одним снятым ограничением (бюджет, окно, переезды) даёт минимальную правку;
  не хватает одной — пара. Текст плана собирает код (`planText`).
- **Вопрос о статусе** («Отменили ли спектакль „Кармен“?», «перенесли ли…»): название — из кавычек или после
  слова «спектакль», «концерт»…; ответ собирает код по записям базы, включая отменённые: отменено / перенесено
  с такой-то даты / билеты проданы / не отменено — со ссылкой на источник. Карточки — только неотменённых.
- Дополнительные указания помощнику (тон, Пушкинская карта и т. п.) — в админке.
- **Трасса и лимиты стоимости** — см. «Защита и фоновые задачи».

### Контрольный набор (`eval/queries.json`, `scripts/eval.mts`)

`npm run eval` прогоняет набор через `runAgent` (источник `eval`, в аналитику не входит) и пишет `eval/report.md`:
дата, коммит, версия промпта (хеш `agent.ts`), модель, токены и стоимость, метрики 1–9 раздела 9.2 с порогами
уровня 4 и базовой линией (поиск по ключевым словам), таблица кейсов с замечаниями и ответы со ссылками на трассы.
Ожидаемый результат каждого кейса считает оракул — проверка всех актуальных событий базы на условия кейса: есть
подходящие — агент обязан показать события, и все они должны выполнять условия; нет — честный отказ (пусто или
«ничего не нашлось — вот ближайшее»). Поэтому набор не зависит от конкретных данных. Точность аргументов — по
первому поиску в трассе; фактическая точность — названия в кавычках, цены, время и даты в тексте ответа сверяются
с событиями ответа (числа из реплики пользователя — его условия, не утверждения). Даты в наборе относительные
(`today`, `weekend`, `next_week`…). `-- --only id1,id2` — часть кейсов, `-- --no-report` — без записи отчёта.
Для кейса с инъекцией в данных в демо-событиях есть «Театральный квиз» с инструкцией в описании.
Метрика 6 — инструмент первого вызова последней реплики (поле кейса `tool`, по умолчанию `search_events`) и его
аргументы. Кейсы с `bot: true` идут от временного пользователя бота; он, его подписки и созданные прогоном
обращения удаляются в конце.

## ИИ-провайдеры и нагрузка (`lib/server/ai.ts`)

- Провайдеры: **GigaChat** (Сбер, серверы в РФ; сертификат Минцифры — `certs/russian_trusted_root_ca.pem`)
  и **любой OpenAI-совместимый** API (OpenRouter, DeepSeek, YandexGPT, Ollama). Выбор, ключи, модель — в
  админке, применяются сразу. Список моделей — из API провайдера (`GET /models`), кэш 10 минут.
- **Очередь.** Бесплатный GigaChat обрабатывает один запрос за раз, на параллельные отвечает 429. Все запросы
  идут через очередь с лимитом одновременных (админка, по умолчанию 1); ожидание — до 60 с.
- **Повторы.** 429 — до трёх повторов с паузой 1,5 / 3 / 6 с; сбой сети или 5xx — один повтор.
- **Предохранитель.** Провайдер, не ответивший после повторов, минуту не используется — запросы сразу идут к
  запасному провайдеру (если включено и настроен) или агент отвечает без ИИ.
- **Кэш** одинаковых запросов — 10 минут.
- **Лимиты GigaChat** — `GET /balance`, остаток токенов по группам моделей (Lite/Pro/Max/Ultra), в админке.

На один запрос пользователя — два обращения к модели (разбор и объяснение), примерно 1,5–3 тыс. токенов.

## Боты (`lib/server/bot-core.ts`, `max.ts`, `telegram.ts`)

Общая логика в `bot-core.ts`: приветствие, команды, сброс диалога (`/start`, `/new`, «Новый поиск»), вызов
агента, хранение диалога в `BotUser`. Ответ — структура `BotReply` (текст, ссылки на события, подсказки),
платформенные модули отображают её своими средствами. Подробно — [BOTS.md](BOTS.md).

Циклы опроса запускаются в `instrumentation.ts` при старте сервера и живут всё время работы: бот выключен в
админке — цикл ждёт, включили — продолжает без перезапуска.

## Защита и фоновые задачи

- **Лимит частоты** (`lib/server/rate-limit.ts`): умный поиск — лимиты на IP и на пользователя бота из админки
  (по умолчанию 600/мин и 10 000/сутки на IP — с одного адреса могут ходить многие; 150/мин и 2000/сутки на пользователя;
  0 — без ограничения). Применяется к сайту и
  API; IP — из заголовка `X-Real-IP` от Caddy) и на пользователя бота. Ответ `429` с `Retry-After`. Счётчики в
  памяти процесса — при нескольких экземплярах приложения нужен общий Redis.
- **Фоновые задачи** (`lib/server/jobs.ts`, запуск в `instrumentation.ts`), раз в минуту:
  прошедшие события (`endsAt`, а без него — начало + 3 часа) получают статус `PAST`; отправляются наступившие
  напоминания (отправщики регистрируют модули ботов через `registerSender`).
- **Аналитика и трассы** (`lib/server/analytics.ts`): `runAgent` с параметром `source` пишет каждый ответ в
  `QueryLog` вместе с трассой — шаги агента (`TraceStep`) и вызовы модели. Вызовы собирает `withAiUsage` из
  `ai.ts` через `AsyncLocalStorage`: `chat()` записывает провайдера, токены (`usage.total_tokens`, без него —
  оценка ~4 символа на токен), задержку, попадание в кэш, ошибки. Стоимость — по цене из настроек.
- **Лимиты стоимости**: перед ответом `runAgent` суммирует `costRub` пользователя за сутки и диалога
  (`dialogKey` — хеш пользователя и первой реплики); превышен лимит — ответ без ИИ, режим `limit`.

## Координаты площадок (`lib/server/geocode.ts`)

Площадки из лент часто приходят без адреса («Башкирский драмтеатр», «Театр оперы и балета, Большой зал»). Фоновая
задача `geocodeVenues` (10 площадок раз в 5 минут, Nominatim с очередью и кешем) пробует адрес, затем варианты
названия (`venueNameVariants`: без зала после запятой, без кавычек, без «государственный академический», «Республики
Башкортостан», «имени …»; «драмтеатр» → «драматический театр»). Не нашлось — центр населённого пункта с пометкой
`Venue.approx`: событие видно на карте (площадки одного города без адреса — одна точка «адрес площадок
уточняется»), в карточке — «точный адрес не указан» без карты и маршрута; поиск «рядом со мной» и переезды в
планировщике такие координаты не используют. Координаты из разметки schema.org (`location.geo`) берутся сразу.
Карта каталога показывает все подходящие события (до 1000), а не одну страницу. Площадку с примерными
координатами модератор уточняет в разделе «Площадки» (адрес → геокодер, или координаты вручную); примерная
площадка, у которой появился адрес, геокодируется заново. Если Яндекс Карты не загрузились (лимит, ключ),
`venue-map.tsx` показывает OpenFreeMap.

Показы одного события (то же название и площадка) в выдаче сводятся в одну карточку: `groupSessions`
(`lib/format.ts`) для каталога, чата и виджета — диапазон дат и «N показов», ссылка на ближайший; `groupItems`
(`bot-browse.ts`) для ботов — строка «ещё показы: …». На странице события — «Другие показы».

## Поиск рядом, карта, SEO

- «Рядом со мной» в помощнике (`NEAR_ME_RE`): без местоположения — ответ `askLocation` (кнопка «📍» на сайте —
  геолокация браузера; `request_location` в Telegram, `request_geo_location` в MAX), запрос повторяется с
  `location` или `"denied"`. Координаты — только в этом поиске: в аргументах инструмента в трассе заменяются
  пометкой, `near` не пишется в фильтр `QueryLog`, в диалог бота не попадают.

- `near=широта,долгота` + `radius` (км): сначала грубый квадрат в БД по координатам площадки, потом точное
  расстояние (гаверсинус) и, при `sort=distance`, сортировка в памяти. У событий в ответе — `distanceKm`.
- Карта (`components/venue-map.tsx`) — Leaflet + плитки OpenStreetMap (бесплатно, с указанием авторства;
  приглушены CSS-фильтром). На главной — вид «На карте» (точки площадок, во всплывающем окне — события),
  на странице события — «Как добраться» и ссылка на маршрут в Яндекс Картах. Кнопка «Рядом со мной» — геолокация
  браузера.
- SEO: `app/sitemap.ts` (актуальные события), `app/robots.ts`, разметка schema.org `Event` (JSON-LD) на странице
  события, картинки-превью ссылок через `next/og` (`app/opengraph-image.tsx`, `app/(site)/events/[id]/opengraph-image.tsx`;
  шрифт Inter в woff — `lib/server/og.tsx`).

## Языки (`lib/i18n.ts`)

Интерфейс сайта — на русском и башкирском; переключатель «Рус / Баш» в шапке ставит cookie `lang`
(`/lang/<код>?back=…`). Словарь — `lib/i18n.ts`, названия месяцев и дней недели по-башкирски — свои (Intl их
не знает). Содержимое событий не переводится. Помощник в башкирской версии получает `lang: "ba"` и отвечает
по-башкирски; быстрые ответы показываются по-башкирски, а отправляются по-русски (их разбирают правила).
`proxy.ts` передаёт текущий путь, чтобы после переключения вернуться на ту же страницу.
**Башкирские тексты — машинный перевод, перед показом проверить с носителем языка.**

Перевод правится без кода: админка → «Сайт» → «Башкирская локализация» (`lib/server/localization.ts`). Выгрузка —
CSV «русский;башкирский» из всех пар `i18nPairs()` (словарь, жанры, быстрые ответы, примеры) и `agentPhrasePairs()`
(фразы помощника, кроме указаний модели); загрузка проверяется целиком (`checkLocalization`) и сохраняется в
настройке `i18n.ba` — только отличия от встроенного, ключ — русский текст. `baText(ru, встроенный)` подменяет
перевод в `tr`, `categoryName`, `quickLabel`, `examplesBa` и фразах помощника; на сервере переводы подгружает
`getLang()` (для `ba`), в клиентский чат они приходят пропсом.

**Возраст не указан.** Фильтр `age` пропускает события с ограничением не старше возраста и без пометки; без пометки
идут в конце (две выборки со сквозной постраничностью в `searchEvents`, у помощника — тоже в конце) и показываются
с подписью «возраст не указан» в каталоге, чате, виджете и боте. Помощник не называет такие события детскими.
Собранное ИИ и присланное организаторами без возраста приходит в модерацию с пометкой «допишите, если известен».

## Настройки (`lib/server/settings.ts`)

Раздел `tuning` — все рабочие числа (таймауты и повторы ИИ, кэш, температура, размеры выдачи, радиус, возрасты,
сроки напоминаний) и тексты помощника; раздел `map` — поставщик карты и ключ Яндекса. Значения вне пределов схемы
заменяются на значения по умолчанию (`.catch()` в zod), поэтому ошибочная настройка не ломает работу.


Разделы `site`, `ai`, `max`, `telegram`, `map`, `mail`, `tuning` хранятся в таблице `Setting` как JSON, схема — zod. Чтение
кэшируется на 5 секунд. Пустое поле в админке → значение из переменной окружения (если задана) → значение по
умолчанию. Секреты в админке не показываются целиком.

## Аналитика спроса (`lib/server/analytics.ts`)

`analyticsSummary` — запросы, стоимость, p95, популярное и «чего не хватает» (тексты запросов без точного
ответа). `coverageSummary` — покрытие афиши: по городам и категориям спрос (запросы к помощнику; город и категория
— из шага `rules` трассы, то есть до ослабления условий) против предложения (актуальные опубликованные события),
пометки «событий нет», «спрос не закрыт», «мало событий»; сетка «город × категория» с пустыми клетками.
Кнопочный поиск в ботах и фильтры каталога в журнал не пишутся.

## Админка (`app/admin`, `lib/server/admin.ts`)

- Пользователи — таблица `AdminUser` (логин, почта, роль `ADMIN` / `MODERATOR`, scrypt-хеш пароля —
  `lib/server/password.ts`). Вход `/admin/login` → сессия в `AdminSession`: в cookie `afisha_adm` случайный
  токен, в базе только его SHA-256; 30 дней.
- Без сессии любой адрес `/admin/*` ведёт на `/admin/login`; роль ниже нужной — 404. Каркас с меню —
  `app/admin/(panel)/layout.tsx`, каждый раздел — отдельная страница и сам проверяет роль.
- Каждое server action начинается с `requireAdmin(роль)` (server actions — открытые POST-эндпоинты).
  Исключения — `app/admin/login/actions.ts` (вход, «забыли пароль», пароль по ссылке): защищены ограничением
  частоты и одноразовыми ссылками.
- Подбор пароля: блокировка логина после 5 неудач на 15 минут (в базе), лимит неудач с IP (в памяти), задержка
  ответа 1 с; для несуществующего логина хеш проверяется так же — время ответа не выдаёт, есть ли логин.
- Почта (`lib/server/mail.ts`): SMTP напрямую (nodemailer) или через посредника — Cloudflare Worker
  `docs/mail-relay-worker.js` (с сервера почтовые порты закрыты). Ссылки из писем — `AdminToken`
  (SHA-256 токена, сброс — 1 час, приглашение — 24 часа, одноразовые).

## Сайт

- Группа маршрутов `app/(site)` — страницы с шапкой и подвалом; `app/widget` — без них (для фрейма).
- Фильтры каталога хранятся в адресе (`?city=…&dateFrom=…`) — подборкой можно поделиться ссылкой.
- Умный поиск (`components/ask-box.tsx`) — чат: до первого вопроса строка ввода с примерами, дальше окно
  диалога (пузыри, подборка компактными карточками под ответом, «Показать ещё», быстрые ответы под последним
  сообщением, «печатает…»). Диалог хранится в памяти страницы; этапы ожидания
  («вы в очереди…»), заготовки карточек, кнопки-подсказки.
- Карточка (`components/event-card.tsx`): плитка на компьютере, строка с миниатюрой на телефоне; без фото —
  иллюстрация категории (`public/illustrations/<slug>.svg`); идущие выставки — «до 11 дек, идёт сейчас».
- Кнопки ботов в шапке (`lib/server/bot-links.ts`) — только включённые боты, имена из API мессенджеров.
- Заголовки безопасности (`next.config.ts`): встраивать во фрейм можно только `/widget`.
