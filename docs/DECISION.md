# Записка о решении: какой агент и почему

Задача — помощник, который подбирает культурные события по свободному запросу и **никогда не выдумывает
мероприятий** (метрика 2 — ноль, порог не смягчается). Всё остальное — скорость, цена, тон ответа — вторично.
Поэтому архитектура строится от вопроса «как сделать выдумку невозможной», а не «как сделать модель умнее».

## Выбранная схема: контролируемый агент

```
реплика ─► модель: ОДИН вызов → JSON {инструмент, аргументы, фильтр}   ┐
       └► правила кода: даты, цены, возраст, «бесплатно», подписка…   ┴► слияние (правила главнее)
                                                                          │
              код проверяет аргументы по схеме и вызывает инструмент: search_events, get_event,
              find_similar, get_venue_schedule, subscribe, save_feedback (≤ 5 вызовов, каждый — в трассе)
                                                                          │
              пусто? код ослабляет условия по порядку и честно говорит, какое снял
                                                                          │
              список событий для ответа формирует КОД ─► модель: 1–2 предложения только по этому списку
```

- **Модель выбирает, код исполняет.** Модель возвращает JSON: какой инструмент вызвать и с какими аргументами.
  Аргументы проверяются схемой, инструмент вызывает код. Модель не обращается к базе и не видит ничего, кроме
  найденных записей.
- **Список событий формирует код.** Карточки под ответом — это записи базы, у каждой есть ссылка на источник.
  Модель лишь связывает 1–2 из них живой фразой. Названия событий из внешних источников передаются ей как
  данные, а не как инструкции. Ссылки из её текста код вырезает.
- **Правила главнее модели.** Частые условия (даты, «до 1000 ₽», «с ребёнком 7 лет», «бесплатно», «подпишите»,
  «отменили ли…») разбирает код. Догадки модели отбрасываются: даты без слов о времени, город, которого нет
  в реплике.
- **Изменение данных — только после подтверждения.** Подписка и обращение к организатору сначала возвращают
  «нужно подтверждение», выполняются после «Подтвердить».
- **Резервный режим встроен, а не добавлен.** Без ИИ (сбой, перегрузка, лимит стоимости) тот же конвейер
  работает на правилах и шаблонном объяснении. Пользователь получает подборку с пометкой, а не ошибку.

## Почему так

| Требование | Как обеспечено | Результат прогона (96 кейсов, 14.11.2026) |
|---|---|---|
| Ни одного выдуманного события | События берутся только из результата инструмента | 0 выдуманных |
| Точность фактов | Цены, даты и время в тексте — из записей; проверяются скриптом | 100 % (≤ 1 неподтверждённое утверждение на прогон) |
| Ограничения выполняются | Условия — фильтр в БД, а не пожелание модели | 100 % запросов с 3+ условиями |
| Честный отказ | Нет данных — «ничего не нашлось»; ослабленное условие названо | 100 % |
| Правильный инструмент | Выбор модели + правила, аргументы по схеме | 99 % |
| Инъекции | Данные отделены от инструкций, ответ собирает код | 10 из 10 кейсов отбиты |
| Задержка | 2 вызова модели на ответ (разбор и объяснение) | p95 — 2,5 с при пороге 6 с |
| Стоимость | То же; кэш одинаковых запросов | 0,87 ₽ за диалог при пороге 3 ₽ |
| Устойчивость | Очередь, повторы, запасной провайдер, работа без ИИ | ответы без ошибок при выключенном ИИ |

Каждый ответ проверяем: в трассе (админка → «Трассы») видны разбор запроса, вызванные инструменты с аргументами,
события-основания, токены и стоимость. Набор контрольных запросов прогоняется командой `npm run eval`.
Отчёт с метриками и сравнением с обычным поиском по ключевым словам — [eval/report.md](../eval/report.md).

## Отклонённые альтернативы

**Свободный вызов функций (tool-calling в цикле).** Модель сама решает, сколько раз и что вызывать.
Отклонено: 3–6 вызовов на ответ вместо двух — дороже и медленнее; у бесплатного GigaChat один поток, и цикл
упирался бы в очередь. Подтверждение перед изменением данных сложнее гарантировать. Модель видит сырые
результаты и может дописать то, чего в них нет. От этого подхода мы взяли полезное: выбор инструмента моделью,
JSON-результат и лимит в 5 вызовов. Отказались только от неконтролируемого цикла.

**Векторный поиск по описаниям (RAG).** Запросы к афише — это структурные условия: «в субботу», «до 1000 ₽»,
«для ребёнка 7 лет». Векторная близость их не гарантирует: она найдёт «похожее», а не «подходящее», и метрика
ограничений провалится. Векторный поиск может дополнить текстовый поиск по описаниям, но не заменить фильтр.

**Модель отвечает целиком, со списком событий.** Самый простой путь, но выдумки и искажения цен и дат не
отловить. Нарушает главное требование задачи.

**Только правила, без ИИ.** Достоверно и бесплатно, это наш резервный режим. Но правила плохо справляются
с перефразировками, опечатками в названиях городов («стерлитакмае»), «похожее на…» и выбором инструмента.

**Дообучение модели.** Нет размеченных данных, афиша меняется ежедневно, а знания модели о событиях всё равно
нельзя проверить. Достоверность даёт поиск по базе, а не память модели.

## Границы применимости

- **Агент знает только то, что есть в базе.** Качество ответов равно качеству данных. Реальные источники пока
  подключаются через раздел «Источники»: на сайте только реальные события, прошедшие модерацию. Метрики посчитаны
  на снимке реальной афиши (временная база, `npm run eval`).
- **Понимает условия, которые выражаются фильтром:** дата и период, город, жанр, цена, «бесплатно», возраст,
  Пушкинская карта, доступная среда, название, площадка, «ближе к центру», «рядом со мной» (только с разрешения на
  геопозицию — кнопка «📍»; без него ищем по всей афише), «самое дорогое / дешёвое». **Не понимает:** время суток
  («после 19:00» не фильтруется), длительность («не дольше двух часов»).
- **Жанры — по справочнику категорий.** Поджанры балет, опера, оперетта, мюзикл ищутся по словам в названии и
  описании самого события (не площадки: «Театр оперы и балета» иначе тянул весь репертуар); остальные поджанры —
  как жанр.
- **Контекст диалога — последние 10 реплик.** В боте после длинного диалога уточнения «а ещё», «дешевле»
  могут потерять прошлую подборку.
- **Подписка через агента — только в ботах.** На сайте аккаунта нет, агент даёт ссылки на ботов. Через API
  подписка оформляется по секретной ссылке.
- **Лимиты частоты считаются в памяти одного процесса.** При нескольких экземплярах приложения нужен общий
  Redis.
- **Метрики посчитаны на собственном наборе.** 10 внешних запросов, которых нет в наборе, по ТЗ готовит
  проверяющий.
- **Башкирский язык помощника** — перевод, требует проверки носителем языка.

## Модель и стоимость

- Основная модель — **GigaChat-3-Ultra** (Сбер, серверы в РФ). Запасной провайдер — любой OpenAI-совместимый
  API (YandexGPT, OpenRouter, свой сервер); переключение в админке без перезапуска.
- Стоимость считается по токенам из ответа API (`usage.total_tokens`) и цене из админки. По умолчанию это
  0,65 ₽ за 1000 токенов — тариф GigaChat Max в синхронном режиме с НДС; отдельной цены для Ultra в прайсе нет.
  Средний диалог на контрольном наборе стоит 0,87 ₽.
- Расходы ограничены лимитами на диалог (10 ₽) и на пользователя в сутки (30 ₽). При превышении помощник
  отвечает без ИИ.
